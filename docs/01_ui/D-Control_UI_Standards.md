# D-Control UI Standards

## Назначение документа

D-Control UI Standards содержит универсальные правила построения пользовательского интерфейса проекта D-Control.

Документ применяется ко всем существующим и будущим компонентам интерфейса: Workspace, Header, Sidebar, Task Card, Task Panel, Toolbar, выпадающим меню, панелям и диалогам.

Стандарты не заменяют Конституцию проекта, Design System или спецификации компонентов. Они фиксируют общие правила взаимодействия и визуального поведения, которые должны соблюдаться во всех частях системы.

## 1. Общие принципы

Интерфейс D-Control должен быть максимально понятным без обучения.

Для одного действия должен существовать один основной способ выполнения. Дублирование допустимо только тогда, когда оно явно снижает количество кликов и не создает неоднозначности.

Пользователь должен выполнять минимальное количество кликов для частых рабочих операций.

Экран не должен быть перегружен. Каждый элемент интерфейса должен иметь понятную цель и помогать ежедневной работе.

Все элементы интерфейса должны использовать единый визуальный язык: одинаковые принципы иконок, hover, active, tooltip, меню, панелей, отступов и анимаций.

## 2. Tooltip

Любой интерактивный элемент, отображаемый только иконкой без текстовой подписи, обязан иметь Tooltip.

Tooltip должен:

- использовать единый компонент;
- иметь одинаковый стиль;
- иметь одинаковые отступы;
- иметь одинаковую анимацию;
- иметь одинаковое время появления;
- не влиять на layout;
- не перекрывать элемент управления;
- не мешать клику по элементу.

Это правило распространяется на:

- Header;
- Sidebar;
- Task Card;
- Task Panel;
- Toolbar;
- будущие панели и диалоги.

Tooltip должен объяснять действие коротко и на языке пользователя.

## 3. Иконки

Все иконки проекта используют Lucide React.

Использование смешанных библиотек иконок не допускается.

Размер, толщина линий и стиль иконок должны быть едиными внутри одного интерфейсного контекста.

Если в Lucide React нет точного смыслового аналога, сначала выбирается ближайшая подходящая иконка из этой же библиотеки. Добавление другой библиотеки требует отдельного архитектурного согласования.

## 4. Hover

Hover должен быть одинаковым во всём проекте для элементов одного типа.

Hover должен быть слабее Active и не должен выглядеть как выбранное состояние.

Hover не должен изменять layout, размеры элемента, положение соседних элементов или ширину контейнера.

Hover используется только для подтверждения интерактивности и не должен отвлекать пользователя.

## 5. Active

Active состояние должно быть хорошо заметным.

Active состояние должно использовать единый стиль проекта и соответствовать Design System.

Active не должен конфликтовать с Hover. Если активный элемент находится под курсором, selected state должен оставаться визуально сильнее hover state.

Active состояние показывает текущий выбранный объект, раздел, вкладку или представление.

## 6. Выпадающие меню

Все выпадающие меню должны работать одинаково.

Открытие и закрытие меню должны иметь единое поведение:

- меню открывается по клику на управляющий элемент;
- одновременно открыто только одно меню одного уровня;
- меню закрывается при выборе пункта;
- меню закрывается при клике вне меню;
- меню закрывается по Escape, где применимо;
- меню не должно оставаться открытым после потери контекста.

Выпадающее меню не должно менять размеры карточки, строки, панели или рабочей области.

## 7. Боковые панели

Все боковые панели проекта открываются поверх Workspace.

Боковые панели не изменяют размеры рабочей области и не сдвигают Kanban как отдельную страницу.

Боковые панели закрываются по:

- кнопке `✕`;
- клику вне панели;
- Escape, где применимо.

Панель должна сохранять рабочий контекст пользователя. После закрытия пользователь возвращается к тому же состоянию Workspace.

## 8. Анимации

Использовать короткие и спокойные анимации.

Рекомендуемая длительность:

`150–250 ms`.

Анимации не должны отвлекать пользователя, задерживать выполнение действий или мешать ежедневной работе.

Допустимые области применения:

- hover;
- active transition;
- открытие popover;
- открытие и закрытие меню;
- появление и скрытие боковых панелей;
- раскрытие и сворачивание компактных блоков.

Декоративные анимации не используются.

## 9. Карточки задач

Карточка задачи должна оставаться компактным элементом Workspace.

Верхняя часть карточки содержит данные задачи:

- название;
- исполнителей, если они отображаются в карточке;
- основные визуальные признаки задачи.

Нижняя часть карточки содержит только метаданные и быстрые действия:

- кнопку `+`;
- приоритет;
- счётчики сообщений;
- счётчики вложений;
- прогресс подзадач;
- другие компактные индикаторы, если они утверждены архитектурой.

Карточка не должна превращаться в самостоятельный экран. Полноценная работа с задачей выполняется в панели задачи.

## 10. Будущее развитие

D-Control UI Standards является живым стандартом.

Документ дополняется по мере развития проекта, появления новых компонентов и принятия новых архитектурных решений.

Новые правила должны дополнять существующую архитектуру, не противоречить Конституции проекта, Design System и спецификациям компонентов.

Если новое UI-решение затрагивает несколько компонентов, все связанные документы должны быть синхронизированы, чтобы между ними не было противоречий.
