# D-Control UI/UX Guidelines

Дата фиксации решений: 30.06.2026

## 1. Основная философия

D-Control - система управления работой предприятия, а не просто канбан-доска.


Workspace является основным экраном системы и главным рабочим пространством пользователя.

Пользователь всегда работает внутри Workspace. Kanban является рабочей областью Workspace, а панель задачи открывается поверх Workspace для полноценной работы с выбранной задачей.

Главная цель интерфейса - ускорять ежедневную работу сотрудников, руководителей и администраторов. Интерфейс должен помогать быстро понять, что требует внимания, где находится задача и какое действие доступно прямо сейчас.

Канбан используется для навигации, обзора и переключения контекста. Основная работа с задачей выполняется в панели задачи.

Базовые принципы:

- максимум полезной информации на экране без визуального шума;
- минимум кликов для частых действий;
- понятные состояния и действия;
- frontend отображает интерфейс и выполняет команды, но не рассчитывает бизнес-права самостоятельно;
- backend является источником прав, доступных действий и эффективных permissions.

## 2. Канбан

Канбан D-Control - это рабочая карта предприятия.

Он нужен для:

- выбора отдела;
- просмотра направлений/колонок;
- навигации по задачам;
- быстрого понимания загрузки и состояния работы;
- перехода к карточке задачи.

Канбан не должен превращаться в перегруженный редактор. Все подробные действия выполняются в панели задачи.

Колонки и разделы должны быть компактными. Карточки задач занимают почти всю внутреннюю ширину колонки, чтобы визуально быть частью рабочего потока, а не отдельными плавающими блоками.

Архив является свернутым разделом канбана, который можно раскрыть при необходимости.

## 3. Панель задачи

Панель задачи - основное рабочее место пользователя.

Требования к панели:

- ширина минимум: 350 px;
- ширина по умолчанию: 450 px;
- ширина максимум: 900 px;
- панель можно изменять по ширине вручную;
- панель находится справа;
- панель не является модальным окном;
- канбан остается доступным и интерактивным;
- выбранная ширина может сохраняться как пользовательская настройка.

В верхней части панели всегда есть строка:

← Закрыть панель

Под ней находится панель действий задачи.

## 4. Структура панели

Целевая структура панели задачи:

1. Строка закрытия панели: ← Закрыть панель.
2. Панель действий задачи.
3. Заголовок задачи.
4. Краткая информация: приоритет, дедлайн, счетчики, важные признаки.
5. Вкладки:
   - Чат задачи;
   - Подзадачи;
   - События;
   - Файлы.
6. Контент активной вкладки.
7. Закрепленное поле ввода сообщения, если активна вкладка Чат задачи.
8. Компактный блок участников внизу:
   - исполнители;
   - наблюдатели.

Исполнители и наблюдатели отображаются компактно внизу под полем ввода сообщения.

## 5. Статус задачи

Статуса задачи как отдельного поля больше нет.

Состояние задачи определяется положением задачи в канбане:

- разделом;
- колонкой;
- этапом жизненного цикла.

Frontend не должен строить отдельную логику вокруг поля status как главного источника состояния. Если backend временно сохраняет статус технически, в UI он не должен восприниматься как самостоятельная бизнес-сущность.

## 6. Приоритет

Вместо статуса используется приоритет.

Приоритет помогает понять срочность и важность задачи, но не заменяет жизненный цикл.

Правила отображения:

- высокий приоритет выделяется визуально;
- обычный приоритет не должен быть ярким;
- приоритет должен быть компактным;
- цвет приоритета не должен конфликтовать с цветами событий, ошибок и unread-индикаторов.

## 7. Чат задачи

Вкладка Чат задачи - основное место обсуждения задачи.

Содержит:

- описание задачи;
- сообщения;
- ответы;
- вложения к сообщениям.

Поле ввода сообщения закреплено снизу вкладки, чтобы пользователь мог быстро написать комментарий или ответ.

Файлы принадлежат сообщениям чата. Вложения отображаются внутри сообщений и дополнительно агрегируются во вкладке Файлы.

## 8. Подзадачи

Подзадачи нужны для декомпозиции выполнения, но не должны превращаться в полноценную вложенную задачу со всеми свойствами основной задачи.

Подзадачи отображают счетчик выполнено/всего, например:

2/5

Правила:

- подзадача технически может оставаться Task через parent_task;
- в UI подзадача имеет название, исполнителей, чекбокс выполнено/не выполнено и комментарии;
- подзадача не должна иметь отдельные файлы, наблюдателей, приоритет и срок в UI;
- один уровень вложенности: задача -> подзадача;
- вложенные подзадачи запрещены.

## 9. События

Вкладка События содержит только системный журнал действий.

Примеры событий:

- задача создана;
- изменено название;
- изменены исполнители;
- задача закрыта;
- задача удалена;
- задача восстановлена;
- задача перемещена между разделами.

События не являются чатом. Комментарии пользователей находятся во вкладке Чат задачи.

События подзадач не должны засорять журнал основной задачи, кроме структурных событий уровня основной задачи, например создана подзадача или удалена подзадача.

## 10. Файлы

Файлы принадлежат сообщениям чата.

Вкладка Файлы - это агрегированный список всех вложений задачи.

Каждый файл должен отображать:

- имя файла;
- автора загрузки;
- дату;
- время;
- возможность скачать;
- при возможности - preview для поддерживаемых форматов.

Для вкладки Файлы синий индикатор новой информации не нужен.

## 11. Индикаторы

Синие индикаторы на вкладках показывают только непрочитанное или новое.

Правила:

- синий индикатор означает, что во вкладке есть новая информация;
- индикатор исчезает после открытия вкладки и нахождения на ней 5 секунд;
- для вкладки Файлы индикатор не используется;
- индикатор не должен использоваться для декоративного выделения.

## 12. Панель действий

Кнопки действий формируются по permissions, которые рассчитывает backend.

Frontend не рассчитывает права самостоятельно.

Frontend получает от backend список эффективных действий и отображает только те кнопки, которые доступны пользователю.

Базовые кнопки действий:

- Готово;
- Доработать;
- Закрыть;
- Удалить.

Кнопки показываются только при наличии эффективных прав.

Кнопка В архив как отдельная кнопка не используется. После закрытия задача автоматически попадает в архив.

## 13. Жизненный цикл задачи

Целевой жизненный цикл задачи:

1. Работа.
2. Все исполнители нажали Готово.
3. Задача попадает в выполненные.
4. Пользователь с правом закрытия нажимает Закрыть.
5. После закрытия задача автоматически попадает в архив.

Выполнение всеми исполнителями не равно закрытию задачи. Закрытие - отдельное управленческое действие.

## 14. Архив

Архив - это свернутый раздел канбана.

Правила:

- закрытая задача автоматически попадает в архив;
- архив можно раскрыть;
- архив не должен занимать много места по умолчанию;
- отдельная кнопка В архив не используется;
- удаление и архивирование - разные действия.

## 15. Цветовая схема

Цвет используется только для смысла, а не для украшения.

Базовые значения:

- синий - новая информация;
- зеленый - успешное действие;
- желтый - предупреждение;
- красный - просрочка, ошибка, удаление;
- серый - второстепенная информация.

Основной синий интерфейса должен оставаться спокойным и рабочим. Акцентные цвета не должны мешать чтению задач.

## 16. Принципы проектирования

Основные принципы UI/UX D-Control:

- D-Control ускоряет работу, а не демонстрирует возможности интерфейса;
- один экран - одна основная цель;
- канбан - обзор и навигация;
- панель задачи - выполнение работы;
- меньше визуального шума;
- высокая плотность информации;
- одинаковые действия должны выглядеть одинаково;
- права приходят с backend;
- frontend не дублирует бизнес-логику permissions;
- каждое новое действие должно отвечать на вопрос: делает ли оно ежедневную работу быстрее?


## Принцип контекстного меню

В D-Control используется единый принцип взаимодействия с объектами интерфейса.

Основные действия должны быть доступны напрямую через интерфейс одним нажатием.

Дополнительные действия размещаются в контекстном меню, обозначаемом кнопкой «⋯».

Контекстное меню должно использоваться одинаково во всей системе.

Правила:

- Клик по объекту открывает его или позволяет быстро изменить основное свойство.
- Кнопка «⋯» всегда открывает дополнительные действия над выбранным объектом.
- Наиболее часто используемые действия должны быть доступны без открытия меню.
- Все основные действия должны также дублироваться в меню «⋯», если это не приводит к неоднозначности.
- Пользователь должен понимать, что если нужного действия нет на экране, его следует искать в меню «⋯».

Примеры применения:

Карточка задачи:

- открыть;
- меню «⋯»: редактировать, изменить приоритет, изменить срок, удалить.

Подзадача:

- клик по названию — переименование;
- клик по исполнителю — смена исполнителя;
- клик по сроку — изменение срока;
- меню «⋯»: переименовать, исполнитель, срок, удалить.

Сообщение:

- меню «⋯»: ответить, редактировать, удалить.

Файл:

- клик — открыть или скачать;
- меню «⋯»: скачать, показать в чате, удалить.


## Принцип быстрых действий

В D-Control все действия разделяются на две категории.

Быстрые действия — операции, которые руководители и сотрудники выполняют десятки раз в день. Они должны быть доступны непосредственно с карточки задачи без открытия панели задачи.

К быстрым действиям относятся:

- Назначение исполнителя.
- Установка или изменение срока.
- Изменение приоритета.
- Создание подзадачи.

Сложные действия выполняются внутри панели задачи или через контекстное меню.

## Правило отображения быстрых действий

На карточке задачи отображается только кнопка `+`.

При наведении курсора на кнопку `+` отображается панель быстрых действий.

Панель содержит:

- 👤 Исполнитель
- 📅 Срок
- 🔥 Приоритет
- ➕ Подзадача

При уходе курсора панель скрывается.

Если пользователь нажимает кнопку `+`, панель закрепляется до завершения работы или клика вне карточки.

## Принцип редактирования

Основные параметры задачи могут изменяться двумя способами.

Быстро — через панель быстрых действий на карточке.

Полностью — через кнопку `Редактировать задачу` внутри панели задачи.

Название и описание задачи изменяются только через режим редактирования.
