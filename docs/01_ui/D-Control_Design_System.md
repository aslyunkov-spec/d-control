# D-Control Design System

Версия: 1.0

## Назначение

D-Control Design System определяет единый визуальный язык проекта D-Control.

Документ фиксирует уже принятые визуальные стандарты интерфейса и задает место для дальнейшего развития дизайн-системы без изменения утвержденной архитектуры проекта.

Все новые компоненты интерфейса должны соответствовать данной дизайн-системе, Конституции проекта, UI/UX Guidelines и спецификациям компонентов.

Дизайн-система не вводит новые функции и не меняет бизнес-логику. Она описывает, как должны выглядеть и вести себя уже принятые элементы интерфейса.

## Основные принципы дизайна

D-Control использует минималистичный современный корпоративный интерфейс.

Основные принципы:

- спокойная цветовая гамма;
- отсутствие лишних декоративных элементов;
- максимум полезного пространства;
- единый стиль всех компонентов;
- высокая плотность информации;
- интерфейс должен быть удобен при ежедневной работе в течение всего рабочего дня;
- простота важнее визуальных эффектов;
- визуальные элементы должны помогать работе, а не отвлекать от нее;
- каждый элемент интерфейса должен иметь понятную цель.

## Цветовая палитра

### Primary

Основной фирменный цвет D-Control:

`#1d588f`

Использование:

- Header Workspace;
- активные элементы;
- основные кнопки;
- акцентные элементы навигации;
- элементы, обозначающие основной рабочий контекст.

Фон рабочей области не является фиксированным.

Пользователь может изменять фон Workspace через настройки внешнего вида. Это является частью архитектуры D-Control и не должно восприниматься как отклонение от дизайн-системы.

### Semantic Colors

Цвет используется только для смысла.

- синий — новая информация, активное состояние, системный акцент;
- зеленый — успешное действие;
- желтый — предупреждение;
- красный — просрочка, ошибка, удаление;
- серый — второстепенная информация.

Декоративное использование цвета не допускается.

### Neutral Colors

Нейтральные цвета используются для:

- фона панелей;
- разделителей;
- второстепенного текста;
- неактивных элементов;
- границ и легких поверхностей.

Нейтральная палитра должна оставаться спокойной и не конкурировать с рабочим содержимым.

## Типографика

В D-Control используется современная читаемая типографика.

Типографика должна поддерживать высокую плотность интерфейса и не создавать лишнего визуального веса.

Рекомендуемые уровни:

### H1

Используется редко, только для крупных системных заголовков.

### H2

Используется для крупных разделов и модальных заголовков.

### H3

Используется для секций внутри панелей и рабочих областей.

### Body

Основной текст интерфейса.

### Caption

Второстепенная информация, даты, счетчики, подписи, метаданные.

Общие правила:

- не использовать лишний жирный текст;
- второстепенную информацию делать меньше и спокойнее;
- заголовки должны быть короткими;
- интерфейс должен говорить на языке пользователя, а не на языке базы данных.

## Библиотека иконок

Для всего проекта используется одна библиотека иконок:

`Lucide React`

Использование нескольких библиотек иконок не допускается.

Причины выбора:

- современный минималистичный стиль;
- lightweight-подход;
- хороший набор базовых UI-иконок;
- визуальная совместимость с корпоративным интерфейсом D-Control.

Если нужной иконки нет в Lucide React, сначала необходимо найти ближайший смысловой аналог в этой библиотеке. Добавление другой библиотеки возможно только после отдельного архитектурного согласования.

## Размеры иконок

Рекомендуемые размеры:

### 16 px

Используется для компактных элементов:

- кнопки в Header;
- действия в карточках;
- маленькие индикаторы;
- compact controls.

### 18 px

Используется для стандартных toolbar-иконок и кнопок средней плотности.

### 20 px

Используется для более заметных действий внутри панелей.

### 24 px

Используется для крупных навигационных элементов, пустых состояний или редких акцентных действий.

Иконки должны быть выровнены по центру своего контейнера.

## Сетка и отступы

Базовая единица сетки:

`4 px`

Все остальные размеры строятся кратно базовой единице.

Рекомендуемые значения:

- 4 px;
- 8 px;
- 12 px;
- 16 px;
- 24 px;
- 32 px;
- 48 px;
- 64 px.

Отступы должны поддерживать компактность рабочего интерфейса. Пустое пространство допустимо только там, где оно улучшает читаемость или разделяет разные функциональные зоны.

## Скругления

D-Control поддерживает пользовательские варианты скругления элементов:

- `Strong`;
- `Medium`;
- `None`.

Выбор скругления сохраняется в пользовательских настройках внешнего вида.

Настройка применяется к основным элементам рабочей области:

- карточкам задач;
- вкладкам;
- колонкам;
- кнопкам;
- полям ввода;
- небольшим UI-контейнерам, если они относятся к рабочей области.

Скругления не должны нарушать плотность интерфейса.

## Тени

Тени используются осторожно.

Правила:

- без тяжелых декоративных эффектов;
- тень должна помогать отделять слой интерфейса от фона;
- карточки могут иметь легкую тень или тонкую границу;
- панели и popover могут иметь более заметную, но спокойную тень;
- декоративные тени не используются.

## Кнопки

В D-Control используются следующие типы кнопок.

### Primary

Основное действие в конкретном контексте.

Используется ограниченно, чтобы не перегружать экран.

### Secondary

Второстепенное действие.

Используется чаще, чем Primary, для обычных рабочих операций.

### Danger

Опасное действие:

- удалить;
- сбросить;
- необратимое действие.

Danger-кнопки должны быть визуально понятными, но не кричащими без необходимости.

### Ghost

Минимальная кнопка без тяжелой визуальной подложки.

Используется для Header, контекстных действий, toolbar-элементов и компактных интерфейсных зон.

### Icon Button

Кнопка только с иконкой.

Используется там, где смысл иконки очевиден или есть tooltip/aria-label.

Правила:

- иконка должна быть выровнена по центру;
- область клика должна оставаться удобной;
- кнопка не должна выглядеть тяжелее своего действия.

## Вкладки

Вкладки отделов визуально напоминают вкладки браузера.

Правила:

- вкладка должна быть визуально приклеена к рабочему пространству;
- активная вкладка является продолжением рабочей области;
- вкладки не должны выглядеть как отдельные плавающие кнопки;
- кнопка `+` оформляется в стиле кнопки создания новой вкладки браузера;
- активная вкладка должна быть хорошо заметна;
- внутри вкладки остается место для будущего индикатора активности.

## Header

Header Workspace является эталоном оформления проекта.

Текущая структура Header слева направо:

1. Объединенная область открытия бокового меню:
   - `≡`;
   - `D-Control`.
2. Вкладки отделов.
3. Кнопка `+` для создания нового отдела.
4. Избранное.
5. Центр активности.
6. Поиск.
7. Кнопка открытия панели задачи.

Правила Header:

- основной цвет `#1d588f`;
- текст и иконки светлые;
- иконки используются из Lucide React;
- кнопка открытия панели задачи отображается только при закрытой панели задачи;
- иконки избранного и активности располагаются рядом с поиском;
- Header не должен ломать Kanban и Task Panel;
- Header задает общий визуальный тон D-Control.

## Карточки задач

Карточка задачи является компонентом Workspace и располагается внутри Kanban.

Правила оформления:

- компактность;
- минимум визуального шума;
- скругление управляется пользовательской настройкой;
- внутренние отступы должны быть достаточны для читаемости, но не создавать пустоту;
- карточка занимает почти всю внутреннюю ширину колонки;
- выбранная карточка выделяется тонкой акцентной полосой, а не полной сменой цвета;
- частые действия доступны через `+`;
- дополнительные действия доступны через `⋯`.

## Панель задачи

Панель задачи является главным рабочим пространством для полноценной работы с задачей.

Стиль панели:

- минималистичный;
- компактные блоки информации;
- максимум полезной площади;
- единый стиль вкладок;
- без тяжелых декоративных рамок;
- содержание важнее оформления.

Панель открывается поверх Workspace, перекрывает Kanban и верхнюю панель, но не является отдельной страницей.

## Цвета приоритетов

Приоритет используется вместо отдельного статуса задачи в пользовательском интерфейсе.

Текущие правила:

- высокий приоритет выделяется компактным акцентным бейджем;
- обычный приоритет не выделяется ярко;
- цвет приоритета не должен конфликтовать с цветами ошибок, предупреждений и unread-индикаторов.

Раздел оставляет место для будущего расширения палитры приоритетов без изменения общей архитектуры.

## Индикаторы и бейджи

Индикаторы используются для компактного отображения состояния или количества.

Типы:

- счетчики;
- уведомления;
- непрочитанные элементы;
- индикаторы активности;
- количество комментариев;
- количество вложений;
- прогресс подзадач.

Правила:

- индикатор должен иметь смысл;
- декоративные индикаторы не используются;
- синий индикатор означает новую или непрочитанную информацию;
- для вкладки `Файлы` unread-индикатор не используется;
- индикатор не должен перегружать карточку или Header.

## Поля ввода

Единый стиль применяется к:

- поиску;
- текстовым полям;
- селектам;
- выпадающим спискам;
- inline-редактированию.

Правила:

- поля должны быть компактными;
- активное состояние должно быть заметным, но спокойным;
- placeholder должен быть коротким;
- поле не должно ломать layout при появлении;
- поля в Header должны быть ниже и легче визуально, чем основные рабочие компоненты.

## Анимации

Анимации должны быть быстрыми, плавными и ненавязчивыми.

Не использовать декоративные анимации.

Допустимые области:

- hover-состояния;
- открытие popover;
- раскрытие/сворачивание компактных блоков;
- смена активного состояния.

Анимация не должна мешать ежедневной работе или замедлять интерфейс.

## Будущее развитие

Этот раздел предназначен для последующего расширения дизайн-системы.

Возможные направления:

- уточнение токенов цвета;
- токены типографики;
- токены теней;
- таблица размеров компонентов;
- спецификация dark theme;
- корпоративные темы;
- правила preview файлов;
- расширение состояний кнопок и полей.

Любое расширение дизайн-системы должно соответствовать Конституции проекта и не противоречить уже принятым UI/UX решениям.
