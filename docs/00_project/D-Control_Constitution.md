# D-Control Constitution

## Назначение

D-Control Constitution определяет основные неизменяемые принципы архитектуры, UX и философии проекта D-Control.

Этот документ является главным архитектурным ориентиром проекта. Все дальнейшие продуктовые, технические и интерфейсные решения должны соответствовать положениям Конституции.

Конституция не является технической документацией, описанием API или перечнем текущих экранов. Она фиксирует фундаментальные правила, от которых зависит целостность системы.

Если новое решение противоречит Конституции, необходимо сначала изменить Конституцию, осознанно зафиксировать новое правило, и только после этого изменять реализацию.

Любая реализация, документация, UI-решение или бизнес-логика, противоречащая Конституции, считается архитектурным отклонением.

## Философия проекта

D-Control — корпоративная система управления работой предприятия.

Основной объект системы — задача.

Задача является центром взаимодействия сотрудников, руководителей, наблюдателей и администраторов. Все коммуникации, файлы, подзадачи, действия и история должны быть связаны с задачей и помогать пользователю выполнить работу быстрее и понятнее.

Канбан используется для навигации.

Канбан показывает структуру работы, расположение задач, отделы, направления и этапы. Он помогает быстро найти нужную задачу и понять текущую картину работы, но не является главным местом выполнения всех действий.

Работа выполняется внутри панели задачи.

Панель задачи является главным рабочим пространством пользователя. Именно там пользователь читает описание, общается, смотрит подзадачи, работает с файлами, видит события и выполняет доступные действия.

Простота интерфейса важнее количества функций.

Функция должна добавляться только тогда, когда она делает ежедневную работу быстрее, понятнее или надежнее. Возможность реализовать функцию технически не является достаточным основанием для ее добавления.

Любой элемент интерфейса должен иметь понятную цель.

Если пользователь не может быстро понять, зачем нужен элемент, где он находится и что произойдет после взаимодействия с ним, такой элемент должен быть переработан или удален.

## Основные архитектурные принципы

Frontend никогда не принимает бизнес-решений.

Frontend отвечает за отображение интерфейса, пользовательское взаимодействие и передачу команд backend. Он не должен самостоятельно рассчитывать бизнес-правила, права доступа, доступность действий или итоговое состояние задачи.

Все права рассчитывает Backend.

Backend является единственным источником прав доступа, effective permissions и допустимых действий пользователя.

Frontend отображает только effective permissions.

Если действие не пришло с backend как доступное, frontend не должен показывать его как активное. Скрытие или отображение кнопки на frontend не является механизмом защиты прав.

Пользователь выполняет действия, а не изменяет статусы.

Пользователь нажимает `Готово`, `Доработать`, `Закрыть`, `Удалить` или выполняет другие осмысленные действия. Система сама переводит задачу в нужное состояние согласно бизнес-правилам.

Отдельного статуса задачи не существует.

Состояние задачи определяется расположением на канбан-доске: отделом, колонкой, разделом и этапом жизненного цикла.

Архив не является статусом.

Архив — это место хранения закрытых задач. Он не должен использоваться как обычный статус или как ручное состояние, которое пользователь выбирает напрямую.

После закрытия задача автоматически перемещается в архив.

Закрытие задачи является управленческим действием. После закрытия система автоматически переносит задачу в архивный раздел.

Комментарии других пользователей редактировать нельзя.

Пользователь может редактировать только собственные комментарии, если это разрешено правилами системы. Комментарии других пользователей не должны изменяться вручную.

История изменений создаётся только системой.

История изменений является системным журналом фактов. Пользователь не создает события истории вручную.

Историю изменений нельзя редактировать или удалять.

История должна оставаться неизменяемой. Исправление ошибки в истории возможно только через отдельное системное событие или административный механизм, специально описанный в архитектуре.

## Основные UX-принципы

Панель задачи является главным рабочим пространством.

Канбан помогает выбрать задачу. Панель задачи помогает выполнить работу.

Чат задачи является центром взаимодействия.

Обсуждение, вопросы, ответы, вложения и рабочая коммуникация должны находиться в чате задачи, а не растворяться по разным частям интерфейса.

Описание задачи является отдельным объектом.

Описание не является первым сообщением чата и не должно смешиваться с обсуждением. Оно задает исходный контекст задачи и редактируется отдельно.

Файлы принадлежат сообщениям.

Файл должен иметь контекст: кто отправил, когда отправил и в рамках какого сообщения. Файлы не должны существовать как безымянные вложения вне коммуникации.

Вкладка `Файлы` является представлением файлов.

Вкладка `Файлы` не является отдельным владельцем файлов. Она показывает общий список вложений, которые принадлежат сообщениям задачи.

События содержат только системные изменения.

События не являются чатом, комментариями или пользовательским описанием. События фиксируют системные факты: создание, изменение, назначение, закрытие, удаление, восстановление и другие действия.

Интерфейс должен говорить на языке пользователя, а не на языке базы данных.

Пользователь должен видеть понятные действия и состояния: `Готово`, `Доработать`, `Закрыть`, `Исполнители`, `Гости`, `Срок`, `Приоритет`. Технические названия полей, internal codes и структура таблиц не должны проявляться в пользовательском интерфейсе.

## Принципы взаимодействия

`+` — быстрые действия.

Кнопка `+` используется для частых действий, которые пользователь выполняет много раз в день: назначить исполнителя, установить срок, изменить приоритет, создать подзадачу.

`⋯` — контекстное меню.

Кнопка `⋯` используется для дополнительных действий над объектом: редактирование, удаление, дополнительные настройки и редкие операции.

Основные действия доступны напрямую.

Частые и важные действия не должны быть спрятаны глубоко в меню, если они нужны пользователю постоянно.

Дополнительные действия находятся в меню `⋯`.

Если действие не является ежедневным или требует осторожности, оно должно быть размещено в контекстном меню.

Любой длинный объект должен поддерживать сворачивание.

Длинные списки, разделы, архивы, истории и второстепенные блоки должны иметь возможность сворачиваться, чтобы сохранять плотность интерфейса и не мешать основной работе.

Пользователь должен выполнять минимальное количество кликов.

Каждое дополнительное действие, экран или подтверждение должны быть оправданы риском, безопасностью или реальной необходимостью.

## Принципы истории изменений

Изменения группируются по сеансу работы пользователя с задачей.

Если пользователь в рамках одного непрерывного редактирования изменил несколько полей, система должна стремиться показать это как одно событие, а не как шумный набор отдельных строк.

Один сеанс = одно событие.

Сеанс работы пользователя с задачей должен восприниматься как единый смысловой блок истории.

Изменения отображаются в понятной форме.

История должна объяснять пользователю, что именно изменилось, без технических терминов и без необходимости знать структуру базы данных.

Формат изменения:

`Старое значение → Новое значение`

Без слов `Было` и `Стало`.

Пример:

`Иван Петров → Анна Смирнова`

`Обычный → Высокий`

`15.07.2026 → 18.07.2026`

## Принципы дальнейшей разработки

Перед реализацией новой функции необходимо:

1. Проверить Конституцию.
2. Проверить UI Guidelines.
3. Проверить существующие спецификации.
4. Только после этого принимать новое решение.

Новые решения должны дополнять существующую архитектуру, а не противоречить ей.

Если новая функция требует исключения из Конституции, это исключение должно быть явно описано и принято до начала реализации.

Если новая функция усложняет интерфейс, она должна доказать, что делает ежедневную работу быстрее, понятнее или надежнее.

Если новая функция дублирует уже существующий механизм, необходимо выбрать один основной механизм и удалить или не развивать дубликат.

Конституция имеет приоритет над локальными решениями отдельных экранов, компонентов и временных реализаций.
